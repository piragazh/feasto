## Part 2: Time Model (Simple & Explainable)

### Available Timestamps

**Primary:** `offline_synced_at` (server-authoritative UTC)
- Always present on offline orders
- Reliable (generated by sync function)
- Represents order creation time (within minutes)

**Not Used:**
- `offline_created_at` (client-generated, no timezone info)
- `created_date` (doesn't capture offline_created_by context)

### Daypart Buckets (5 Windows)

| Daypart | UTC Hours | Pattern |
|---------|-----------|---------|
| Morning | 05:00–10:59 | Breakfast, opening prep |
| Lunch | 11:00–13:59 | Peak lunch period |
| Afternoon | 14:00–16:59 | Post-lunch, pre-dinner gap |
| Dinner | 17:00–21:59 | Peak dinner period |
| Late | 22:00–04:59 | Late night, overnight |

### Day-of-Week Grouping

- **7-day report:** Monday–Sunday (all individual)
- **Classification:** Weekend (Sat/Sun) vs Weekday (Mon–Fri)
- **Timezone:** UTC, no conversion (documented limitation)

### Hourly Resolution

- **24-hour array:** Hour 0–23 (UTC)
- **Per-hour metrics:** Count, flagged, flagged_rate
- **Trend visualization:** Line chart showing rate by hour

## Part 3: Temporal Metrics (8 Per Time Window)

### Per-Daypart / Per-Day Metrics

| Metric | Formula | Meaning |
|--------|---------|---------|
| Total Orders | Count | Volume |
| Flagged Count | `needs_review=true` | # problematic |
| Flagged Rate | Flagged / Total × 100 | % problematic |
| Escalated Count | `offline_review_status='escalated'` | # escalated |
| Escalation Rate | Escalated / (Flagged + Escalated) × 100 | % of issues escalated |
| Order Volume | Count | Business metrics |
| Concentration | % of total | Operational pattern |
| Hour Distribution | {hour: count} | Peak hours within daypart |

### Aggregations

- **Busiest daypart / day**

## Part 4: Temporal Outlier Rules (5 Types)

### Rule 1: High Flagged Rate in Daypart
- **Threshold:** >20% (min 3 orders)
- **What it means:** Daypart-specific orders consistently flagged
- **Possible causes:** Network outage during shift, understaffing, POS misconfiguration
- **Action:** Check POS logs for shift, review staffing, verify network health

### Rule 2: High Escalation Rate in Daypart
- **Threshold:** >50% of flagged (min 2 escalated)
- **What it means:** Issues in this daypart are severe
- **Possible causes:** Manager stricter at certain hours, complex orders, fatigue
- **Action:** Review escalated orders, assess manager judgment, check workload

### Rule 3: Daypart Concentration
- **Threshold:** >40% of all orders in one daypart
- **What it means:** Operational pattern — most offline activity concentrated
- **Possible causes:** Network degradation at peak, system design, business model
- **Action:** Verify if operational/expected, monitor for changes

### Rule 4: Weekend vs Weekday Anomaly
- **Threshold:** >15 percentage point difference in flagged rate
- **What it means:** Weekend operates significantly differently
- **Possible causes:** Different staff, higher volume, different order types
- **Action:** Compare staffing, review if volume is driver

### Rule 5: Specific Hour with High Flagged Rate
- **Threshold:** >30% flagged (min 2 orders)
- **What it means:** Specific hour(s) consistently problematic
- **Possible causes:** Known outage window, delivery surge, shift change
- **Action:** Correlate with external events, check system health

## Part 9: Timezone Limitations

### What Happens

- **All times are UTC** (from `offline_synced_at`)
- **No timezone conversion** (Restaurant entity has no timezone field)
- **Daypart buckets are UTC-fixed** (05:00–22:00 UTC always)

### Impact Example

| Scenario | UTC Time | Daypart | Reality |
|----------|----------|---------|---------|
| UK restaurant, winter (GMT) | 20:00 | Dinner | ✅ Correct (20:00 local = 20:00 UTC) |
| UK restaurant, summer (BST) | 20:00 | Dinner | ❌ Wrong (20:00 local = 19:00 UTC, is Afternoon) |
| US East (EST) | 20:00 | Dinner | ❌ Wrong (20:00 local = 01:00 UTC next day, is Late) |

### Workaround

- Admins know their restaurant's UTC offset
- Can mentally adjust interpretation
- Example: "Afternoon spike (14–17 UTC) is actually 15–18 local (BST)"
- Weekend signal unaffected (calendar days are universal)

### Future Solution

- Phase 4: Add `restaurant.timezone` field
- Recalculate dayparts in local time
- Dashboard adjusts to restaurant's timezone

### Documented

✅ Clearly noted in dashboard UI  
✅ Explained in `OFFLINE_TEMPORAL_ANALYTICS.md`  
✅ No false claims about "local time"
